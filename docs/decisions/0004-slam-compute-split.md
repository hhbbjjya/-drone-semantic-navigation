# ADR 0004：SLAM 前端在機載、重型最佳化在筆電

- 狀態：採用（架構方向）；SLAM 系統與 IMU 來源待定
- 日期：2026-10-30

## 背景
- 機載 Orin Nano 算力、記憶體與功耗有限，且與相機、飛控共用。
- 全域 BA、位姿圖最佳化、迴圈閉合的計算量隨地圖成長，不適合在機上跑。
- 無人機的位置控制需要**每一幀都準時**的位姿；任何依賴無線網路的環節都可能延遲或中斷。

## 決定
| 層 | 位置 | 內容 |
|---|---|---|
| 前端（硬即時） | Orin Nano | 追蹤、局部建圖／VIO、輸出位姿給 PX4、挑選關鍵幀 |
| 後端（軟即時） | 筆電 RTX 5070 | 迴圈偵測、全域最佳化、地圖合併，回傳關鍵幀修正 |
| 語意（非即時） | 桌機 RTX 5070 Ti | VLM / VLA，產生語意目標 |

設定上對應的角色名稱：`onboard`（Nano）、`backend`（筆電）、`vlm`（桌機）。
原本筆電角色叫 `slam`，改名為 `backend`，因為 SLAM 現在跨兩台機器，角色名稱不應暗示 SLAM 只在筆電。

## 失效模式（必須在程式中實作，不只寫在文件）

| 情境 | 機載行為 | 理由 |
|---|---|---|
| 筆電失聯 | 前端繼續輸出位姿，標記「無全域修正」；漂移超過閾值或逾時 → 懸停或降落 | 飛控不得依賴網路 |
| 筆電回傳延遲很大的修正 | 只套用時間戳仍在可接受範圍內的修正，舊修正丟棄 | 太舊的修正會把當前位姿拉錯 |
| 修正造成位姿跳變 | 以錨點轉換平滑套用，並遞增 ODOMETRY reset counter | 直接跳變可能讓 PX4 EKF 拒收或劇烈修正 |
| 前後端 `slam/core` 版本不一致 | 後端拒收並回報 | 靜默讀錯資料比直接失敗更危險 |
| 桌機（VLM）失聯 | 不影響定位；語意任務暫停 | 語意層最不即時 |

## 待決定（各自另寫 ADR）
1. **SLAM 系統**：需要能自然拆成「機上 VIO＋遠端後端」的系統。評估時優先看：前後端是否本來就是分開的程序、是否支援雙目＋IMU、在 Orin Nano 上的即時性。教授希望避免 ORB-SLAM 類黑箱，這也是評估條件之一。
2. **IMU 來源**：Pixhawk 的 IMU 經 MAVLink 傳到 Nano，會有延遲與抖動，時間對齊困難；另一個選項是在 Nano 上加獨立 IMU，或做硬體觸發同步。這直接決定 VIO 的品質，需先做小實驗量測時間偏移與抖動。
3. **通訊介面**：ROS 2（發行版見 ADR 0003）或自訂傳輸；關鍵幀的壓縮方式與頻寬上限。

## 後果
- `slam/core/` 成為前後端的共同依賴，修改需同時測兩端。
- 論文可以量化一個清楚的問題：把最佳化移到筆電，精度提升多少、延遲與斷線風險多少。
